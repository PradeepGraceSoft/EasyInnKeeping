# Playwright Automation Standards

These standards are used by the Playwright Automation Agent and the Codex project rules.

## Stack

- Playwright TypeScript
- Page Object Model via `src/pages/`
- Fixture-based test setup via `src/fixtures/pms.fixture.ts` for authenticated
  PMS tests and `src/fixtures/sso.fixture.ts` for explicit login flows

## Project layout

- Page objects: `src/pages/` extend `BasePage` from `src/utils/BasePage.ts`
- Fixtures: `src/fixtures/pms.fixture.ts`, `src/fixtures/sso.fixture.ts`, and
  `src/fixtures/TestDataGenerator.fixture.ts`
- Tests: `tests/**/*.spec.ts`, grouped by application feature
- Session utilities: `src/utils/LoginSessionStorage.ts` and `src/utils/PmsSessionUtils.ts`
- Generated property sessions: `LoginSessionStorage/{PropertyID}.json` (gitignored)
- Constants: `src/constants/`
- Test data: `src/test-data/` and `src/utils/TestDataGenerator.ts`
- DB helpers: `src/utils/DBHelper/`
- Agent CLI: `npm run agent -- <command>`

## Page object rules

- Extend `BasePage`
- One action per method
- Return `Promise<void>` for actions and verifications
- Prefer `getByRole()` for new locators
- Never use `waitForTimeout()` in new code
- Reuse existing methods before adding new ones
- Group locators and methods with section header comments

### Locator scoping and strictness

- Scope locators to the active dialog, form, table row, or component that owns
  the control. Do not use a page-wide role/name locator when the page can
  contain multiple forms or dialogs with the same accessible name.
- Treat a strict-mode violation as a page-object defect. Fix the locator scope
  or the UI contract; do not hide it with arbitrary `.nth()` calls.
- Use `.first()` only when duplicate controls are an intentional part of the
  rendered UI (for example, responsive desktop/mobile action links) and add a
  comment explaining why the first control is the correct one.
- When selecting a row by text, include enough identifying data to select one
  row, then scope all row actions from that row. Validate the row is visible
  before clicking its action.
- For controls inside a dialog, define the dialog locator first and derive its
  fields and buttons from that locator. Prefer the visible/active dialog when
  multiple dialogs may exist.

### UI synchronization

- Synchronize on explicit UI or network conditions, not elapsed time. Wait for
  the relevant spinner/progress indicator to finish, the expected value to be
  applied, the dialog/overlay to appear or disappear, or the expected response
  to complete.
- Before clicking Save or another control that must receive pointer events,
  verify that transient menus, autocomplete panels, date pickers, confirmation
  dialogs, and CDK overlay backdrops are closed. If the application can show a
  business confirmation after an edit, handle that confirmation in the page
  object before returning from the edit method.
- A method that changes dates, rates, guest details, or other asynchronously
  calculated fields must wait for the calculation/update to complete and
  verify the resulting field value before exposing the next action.
- Save helpers must wait for the active form to be ready, click the scoped Save
  button, and await the save success condition tied to that click. Do not use a
  previously visible snackbar as proof that the current save completed.
- Do not add retries, forced clicks, or sleeps to mask an overlay, stale
  element, or race. Diagnose and wait for the condition that makes the action
  valid; preserve genuine application failures.

## Test rules

- Import `{ test, expect }` from `src/fixtures/pms.fixture` when the test needs
  to start on the authenticated PMS reservation list.
- Use `src/fixtures/sso.fixture` for login, OTP, logout, staff/manager role
  scenarios, or other application flows that must control authentication.
  It provides page objects and helpers without automatically logging in.
- Use `SSOUsers`, `AlertMessages`, and `ConstNames`
- Call `dbHelper.resetSettings()` when SSO state must be reset
- Always `await` page object methods
- Use `verify*` methods for UI assertions
- Use `expect()` in tests for data checks
- Do not compromise a scenario flow to make a test pass. If the application
  exhibits a real defect, preserve the scenario and let the test fail.

### Test file ordering

- Declare each scenario as an individual, explicitly named `test()` by default.
  For example, Today and Tomorrow KPI checks should be separate test declarations,
  not generated by a loop over a single day parameter.
- Use a shared parameterized test definition only when the same scenario varies
  across multiple parameters. Pass each parameter set to that definition and
  include the relevant values in the test title so each case is identifiable.

- Keep imports and shared declarations first, followed by all test cases and
  `test.describe` blocks. Place helper functions at the bottom of the spec,
  after all tests.
- Append new scenarios at the end of the relevant `test.describe` block,
  before the helper-function section. Do not insert new tests above existing
  scenarios or below helper functions.

### PMS session setup

- Use the PMS fixture for new authenticated PMS specs. It extends the SSO
  fixture, so existing page-object and database fixtures remain available.
- Let the fixture load `LoginSessionStorage/{PropertyID}.json` through
  Playwright's `storageState` fixture before the test page is created. Keep
  Playwright's built-in context lifecycle, options, tracing, and per-test isolation.
- Validate the session on the canonical `PMSUI-NG/list` route in each test's
  page. Require the reservation-list UI to be visible; a URL or cookie expiry
  check alone is not proof of authentication.
- When state is missing, unreadable JSON, mismatched with the stored identity,
  or rejected by the application, run the normal credentials/OTP flow. Wait
  for the reservation list to initialize before saving fresh state.
- Keep file loading, validation, and saving in `LoginSessionStorage`; use
  `PmsSessionUtils` for the configured property and login orchestration.
  Do not duplicate this logic in specs or page objects.
- Do not add a login `beforeAll`/`beforeEach`, call `propertyLogin()` again, or
  create another context to authenticate when using `pms.fixture`. Test actions
  such as clicking Setup run after the fixture has validated authentication.
- Keep session JSON files out of source control and logs. The directory is
  runtime data, not a utility-code or test directory.
- `PmsSessionUtils.ensureAuthenticated(page, dbHelper)` remains available for
  callers outside the PMS fixture. Those callers must select the property in
  `ConfigManager` and connect the database for OTP retrieval. Prefer the fixture
  in specs so saved state is applied before page creation.
- Use the BridgePay spec as the migration example. Existing specs importing
  `sso.fixture` do not automatically opt into the new PMS fixture.

## Timeout rules

- The global Playwright action timeout is 15 seconds; a missing or
  non-interactable locator must fail within that limit.
- A test-level timeout is the total workflow budget, not a locator-wait
  allowance. Do not rely on it for ordinary UI actions.
- The authenticated PMS page fixture has its own 90-second setup budget for
  session validation and OTP fallback. Do not copy this as a blanket test or
  locator timeout; reservation-list validation remains bounded to 10 seconds.
- For known asynchronous behavior, use a focused `expect.poll()` or locator
  assertion with an explicit, bounded timeout and explain the condition.
- When a test loops through configurations, set a bounded `test.step()` timeout
  so one failing configuration cannot consume the entire test budget.

## Error reporting rules

- Every failed test must communicate what the user expected the application to
  do, not only which locator timed out. The message belongs in the page-object
  validation or action method that knows the expected behavior.
- For a known business expectation, wait explicitly for the control or state
  and throw a concise business-facing error when it is unavailable.
- Include the screen feature, the expected behavior, and the bounded wait when
  that wait is meaningful.
- Do not use a custom reporter or external log processing to create
  business-facing error messages.
- Do not use `waitForTimeout()` to improve errors. Use retrying locator assertions
  or `expect.poll`. `locator.isVisible()` checks immediately; its timeout option
  does not wait for a control to appear.
- Use this pattern for application-specific failures:
  `<Feature> did not <expected behavior> within <bounded duration>.`
- Example: `The email editor did not finish loading the "Merge Tags" menu item
  within 45 seconds.`
- State the user-visible expected behavior in errors for known business rules;
  do not expose only a raw locator or action timeout.
- Put the message in the page-object validation method itself; do not rely on
  report post-processing to explain the failure.
- Apply this requirement to every page-object verification and interaction that
  represents a business step, including room availability, booking navigation,
  totals, confirmation details, and reservation summaries. A bare Playwright
  locator timeout is not sufficient for these checks.

  ```ts
  await expect(
    mergeTags,
    'The email editor did not finish loading the "Merge Tags" menu item within 45 seconds.',
  ).toBeVisible({ timeout: 45_000 });
  ```

## Reservation cleanup and reporting

- Keep `tests/OnlineBooking/Rates.spec.ts` free of test annotations as requested.
  Track cleanup state in memory; the reservation-annotation guidance below
  does not apply to this spec. Annotations are never a substitute for validation
  messages in page objects.

- When a test creates a reservation, delete it in that test's `finally` block;
  do not use a shared `afterEach` cleanup for the reservation.
- Preserve the reservation when that particular test fails so it can be
  investigated. Track failures with a `try`/`catch` flag and rethrow the
  original error before conditionally deleting in `finally`; do not rely only
  on `test.info().status` from inside `finally`.
- As soon as the confirmation number is available, add it to the Playwright
  test annotations for easy access in the report:

  ```ts
  test.info().annotations.push({
    type: "reservation",
    description: confirmationNumber,
  });
  ```

- The reservation annotation must be added before the first assertion that can
  fail after reservation creation.

## Agent workflow

1. Inspect project: `npm run agent -- inspect`
2. List templates: `npm run agent -- templates`
3. Show template steps: `npm run agent -- template shared-find-list`
4. Generate from template: `npm run agent -- from-template shared-find-list "My test title"`
5. Find page: `npm run agent -- find-page ReservationPage`
6. Check method: `npm run agent -- search-method ReservationPage clickSaveButton`
7. Convert recording: `npm run agent -- convert recorded.ts`
8. Full plan: `npm run agent -- plan "Create test for New Reservation"`

## Do not

- Duplicate methods that already exist on a page class
- Put locators directly in test files
- Import `@playwright/test` test runner in spec files unless the file is a page object or utility
- Create a separate `PageObjectManager`; fixtures are the access pattern for this project
